# Curated GEO Product Selection Design

## 总纲

> 我觉得在精不在多，列出来了100个甚至一千个烂产品不如精选出来真正的有效的能帮助各类用户在各种场景下解决问题的产品。

ARIS-GEO 的公开交付物不再以覆盖对象数量证明价值。市场发现的长名单继续保留为
内部研究数据，但不再面向普通读者展示。公开报告只呈现能够说明“为谁、在什么场景、
解决什么问题、凭什么可信”的精选产品和开源项目。

## 问题根因

当前体系存在四个结构性偏差：

1. **发现标准被误用为推荐标准。** 一个对象只要有可识别官网和 GEO/AI 搜索描述，
   就能进入市场地图；这只能证明“存在”，不能证明“有效”。
2. **深档代表资料丰富，不代表能力优秀。** 进入深档主要依赖公开材料是否足够完成
   字段填充，因此营销资料充分的普通产品可能比低调但有效的项目更显眼。
3. **评分没有直接衡量用户价值。** 透明度、定价、许可证和活跃度是必要辅助信息，
   但不能回答产品是否能定位失败、返回原始证据、推动优化或验证因果。
4. **不同形态被放进同一个阅读路径。** 商业监测 SaaS、自托管工具、研究测试床、
   Prompt Pack 和服务商工具解决的问题不同，无法用同一套菜单或总分公平比较。

## 目标

重构后，读者应能在五分钟内回答：

- 我的企业和场景应该优先试哪一类工具？
- 哪些产品已经有足够公开证据进入 PoC？
- 哪些只是值得观察，尚不足以推荐？
- 哪些常见工具形态解决不了关键问题？
- 一个商业产品或开源项目怎样才能进入精选名单？
- 为什么透镜GEO这类强调真实交互和证据返还的产品会被识别出来？

## 公开层与研究层分离

### 研究层：完整候选池

`wiki/market-map.json` 继续保存全部可识别对象，用于：

- 去重和发现历史；
- 后续证据补全；
- 市场变化研究；
- 防止重复搜索；
- 机器分析和审计。

研究层不构成推荐，不在 README 或最终报告中渲染百项清单。

### 公开层：精选决策报告

公开报告只展示三种状态：

1. **精选 PoC 候选：** 已通过硬门槛，在明确场景中具有相对优势，值得真实试点；
2. **值得观察：** 方向或局部能力有价值，但关键证据、终端覆盖或成熟度不足；
3. **不进入推荐：** 只做结果统计、无法返还证据、功能过粗，或不能证明比简单脚本
   多解决了什么问题。

“不进入推荐”不需要逐个点名全部弱产品；报告按失败类型解释淘汰原因，避免再次制造
无价值长名单。

## 两阶段筛选漏斗

### 第一阶段：硬门槛

商业监测产品必须同时满足：

1. 有明确的 GEO 监测产品，而不是只有代运营或概念营销；
2. 至少覆盖一个目标用户真实使用的 AI 搜索入口；
3. 能返还原始回答、引用、截图或录屏中的至少一种可复核证据；
4. 支持固定问题集或可重复运行，不是一次性品牌检测；
5. 能说明至少一个具体用户场景及相应输出；
6. 不以无法复核的单一黑箱总分作为唯一交付；
7. 公开材料足以确认产品边界和主要限制。

开源项目必须同时满足：

1. 存在可运行代码和明确许可证，不是只有 README、提示词或资源清单；
2. 实现自身采集、数据处理、分析或实验逻辑，而不是只包装一次模型调用；
3. 能保存原始结果和运行配置；
4. 提供可复现安装/运行路径；
5. 有覆盖项目自身核心逻辑的测试，或可复现研究基准；
6. 近期仍可运行，依赖与目标平台没有明显失效；
7. 能明确说明适用边界，不以 Star 数作为有效性代理。

未通过硬门槛的对象仍可留在研究层，但不得进入公开推荐。

### 第二阶段：场景价值评审

通过硬门槛后，不计算一个跨场景总分，而按六个维度形成证据卡：

| 维度 | 核心问题 |
| --- | --- |
| 问题价值 | 它解决了哪类用户的哪个高价值决策？ |
| 测量真实性 | 数据来自真实 Web/App、浏览器自动化、API 还是人工样本？ |
| 证据可复核 | 能否回到原始回答、引用、截图、录屏和运行配置？ |
| 诊断深度 | 能区分终端、候选、引用、提及、推荐和行动中的哪些阶段？ |
| 优化闭环 | 能否把观察转成可检验的内容/渠道假设，并保留 holdout？ |
| 可实施性 | 成本、部署、权限、导出、维护和团队能力是否适合目标用户？ |

产品只有在至少一个场景中形成明显相对优势，才进入“精选 PoC 候选”。公开资料无法
证明的能力保持未知，不能用合理推测补齐。

## 商业产品与开源项目分轨

### 商业产品精选轨

重点关注：

- 国内真实引擎和终端覆盖；
- 账号、地区、模式和重复采样控制；
- 原始证据返还；
- 企业权限、导出和服务稳定性；
- 同一供应商监测与优化时的利益冲突控制；
- 试点成本和退出能力。

### 开源项目精选轨

重点关注：

- 是否真正可运行；
- 是否实现稳定采集和数据模型；
- 是否保存实验配置与原始结果；
- 是否有测试、基准和清楚的维护状态；
- 能否成为企业的独立复核工具或实验底座；
- 相比几十行 API 脚本多解决了什么。

论文、测试床和 Prompt Pack 可作为“研究参考”单列，但不得与生产工具共享推荐标签。

## 场景精选结构

最终报告按用户任务给出少量候选：

| 场景 | 主要问题 | 入选所需能力 |
| --- | --- | --- |
| 国内品牌审计与品牌安全 | 回答是否真实、错误事实发生在哪里 | 真实交互、录屏/快照、原始回答、国内引擎 |
| 中小企业低成本基线 | 是否出现、被谁替代、趋势如何 | 免费/低价、固定问题、原始结果、易上手 |
| B2B 长决策链 | 比较、方案和信任问题中是否进入短名单 | 长问题、引用、事实核验、PC/Web 场景 |
| 国内消费与本地服务 | 手机用户实际看见什么 | iOS/Android/小程序真机、地区与账号控制 |
| 跨境电商与 DTC | SKU、商品卡和购买入口是否出现 | AI Shopping、Feed、价格、国家和商品级数据 |
| 受监管行业 | 是否能审计和追责 | 原始证据、版本、留存、权限、幻觉/错误事实 |
| 自建与独立复核 | 如何避免完全依赖供应商自有分数 | 可运行开源代码、配置、原始数据、测试和导出 |
| 内容与渠道实验 | 写什么、发哪里才真正有效 | 候选/引用漏斗、处理组、holdout、传播时间线 |

每个场景只推荐 1–3 个产品；没有产品通过门槛时，明确写“当前没有足够证据的推荐”，
不得为了填满表格降低标准。

## 透镜GEO如何被筛选出来

透镜GEO不因菜单数量或厂商宣传进入精选，而因其公开材料对“国内品牌审计”场景形成
清楚的证据链：

- 覆盖多个国内主流 AI 平台；
- 声称使用中立账号模拟真实访客；
- 保存从提问到回答的完整屏幕录制；
- 按日追踪品牌排名、口碑和错误事实。

这些能力直接解决“监测结果能否复核”的关键问题，因此足以进入审计型 PoC 候选。
同时，报告必须保留其限制：逐引擎 Web/App 矩阵、重复次数、模型版本、导出/API 和
统计误差仍未公开。它是“公开证据支持的优先 PoC 候选”，不是“已经独立验证效果的
绝对第一名”。

## 报告结构调整

`docs/FINAL_REPORT.md` 调整为：

1. 总纲与精选结论；
2. 为什么百项清单无法帮助决策；
3. 精选方法、硬门槛和淘汰规则；
4. 按用户场景给出的精选商业产品；
5. 精选开源项目与研究参考；
6. 透镜GEO等代表产品为什么入选；
7. 没有足够产品通过门槛的能力空白；
8. 数据验证、利益冲突和采购 PoC；
9. 固定问题集与内容×渠道实验；
10. 研究边界和机器可读候选池入口。

README 只保留总纲、精选报告入口、少量结论和复现命令。编译区只显示数据日期和
研究层说明，不再渲染全球市场地图。

## 测试与验收

自动化测试必须锁定：

- README 不包含全球百项产品表；
- 最终报告包含总纲原句；
- 最终报告明确研究长名单不等于推荐；
- 最终报告分别定义商业产品和开源项目硬门槛；
- 每个精选项必须包含场景、入选理由、证据、限制和推荐状态；
- 报告存在明确的“不足则不推荐”规则；
- 透镜GEO进入国内品牌审计场景的优先 PoC 候选；
- `wiki/market-map.json` 和产品深档继续保留，研究数据不被删除；
- 构建、证据严格校验、评分检查和全部测试继续通过。

## 非目标

- 不根据现有公开资料宣布任何厂商已经被真实采购验证；
- 不生成新的跨场景综合总分；
- 不因为长名单从报告消失而删除研究数据；
- 不强行给每个用户场景安排一个推荐产品；
- 不用 Star、营销数字或功能数量替代有效性判断；
- 本轮不进行所有厂商的付费实测或真机采集。
